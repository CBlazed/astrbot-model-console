## 2. P0 逐项结论与证据

### 2.1 D02 错误响应脱敏 — PASS

实现：`src/server.mjs:26-35` 只放行 `id/backupId/outcome/code` 四个字段并校验格式；`src/server.mjs:38-44` 把 apply 结果的 `backupId` 归一到 UUID basename，非 UUID 直接删除；`src/engine.mjs:6` 的 `backupShortId` 与 `src/engine.mjs:19` 的审计写入分离，审计仍拿原始绝对路径。

测试证据（`test/p0-integration.test.mjs`）：

- 构造 `Error('BACKUP_FAILED')`，`details` 同时含 `backupId: 'C:\Users\alice\AppData\Local\...\state\backups\<uuid>'`、`path:'C:\Windows\System32'`、`token:'audit-token-do-not-leak'`、`authorization:'Bearer ...'`。POST `/apply` 返回 409，body **精确等于** `{error:'BACKUP_FAILED',id:<uuid>,outcome:'not-written',code:'BACKUP_FAILED'}`，序列化文本不含 `C:\`、`AppData`、`Users`、`alice`、`System32`、`backups`、令牌或 `Bearer`，且键集合只允许白名单。
- 非代码型错误（message 内嵌绝对路径）经 `knownError` 折叠为 `OPERATION_FAILED`，POST `/plans` 返回 409，body 仅 `{error:'OPERATION_FAILED'}`，无路径/令牌。
- `/apply` 成功：fake engine 返回绝对路径 + UUID basename，HTTP 响应只含 `backupId: <uuid>`，不含临时目录、`backups` 或分隔符；无法归一为 UUID 的 `backupId` 被删除而非原样回传。
- 对照项：路径形式 `backupId` 被 409 白名单丢弃；UUID 短 id 与完整 UUID 被接受。这与 `test/server-ui.test.mjs` 的既有断言一致，无回归。

### 2.2 D01 空 embedding/rerank 拦截 — PASS

实现：`src/engine.mjs:16` 把索引迁移拦截从 `if(change.value)` 分支内移到 `else if`，空字符串与非空值都抛 `INDEX_MIGRATION_REQUIRES_SEPARATE_WORKFLOW`。

测试证据：真实 `Engine` + fake gateway，对 `astrbot_plugin_livingmemory` 的 `provider_settings.embedding_provider_id`（embedding）和 `recall_engine.rerank_provider_id`（rerank）分别传 `''` 与能力匹配的模型 id，四种组合全部拒绝，且 `engine.plans.size === 0`（被拒请求不留计划）；对照组 `astrbot_plugin_group_chat_plus` 的普通 llm 字段清空仍可计划，证明拦截只针对索引类 capability，没有误伤普通空值语义。

### 2.3 备份 UUID 短 id / 审计完整路径 — PASS

实现：`src/engine.mjs:6`、`src/engine.mjs:19`。

测试证据：`backup` 返回 `C:\state\backups\0243f684-e8ed-44ac-8c95-657df32890aa` 时，`engine.apply` 成功结果 `backupId === '0243f684-...'`（正则 UUID，且不含 `:`、`\`、`/`）；`apply-start` 与 `applied` 两条审计事件的 `backupId` 均为完整 `C:\state\backups\...`。失败路径同理：抛 `NETWORK_LOST` 时 `error.details = {backupId:<uuid>, outcome:'possibly-written', id:<uuid>}`，不含盘符，而 `apply-failed` 审计仍保留完整路径。

### 2.4 D05/D04 状态目录与数据发现 — PASS

实现：`src/config.mjs:15-19`（`resolveStateDir` 优先级 `MODEL_CONSOLE_STATE` > `%LOCALAPPDATA%\AstrBotModelConsole\state` > `<tmp>/AstrBotModelConsole/state`，纯函数不落盘）；`src/config.mjs:26-47`（`discoverAstrBotData`：`ASTRBOT_DATA` 直接胜出；扫描 `.astrbot_launcher/instances/*/core/data` 与 `.astrbot/data`；恰好 1 个才返回，0/多个抛 `ASTRBOT_DATA_REQUIRED` 且带 `candidates` 计数，不泄露 ENOENT）；`src/config.mjs:54-58`（旧 `./state` 只提示不迁移）。`src/server.mjs:71-83` 先解析状态目录再取锁，`src/server.mjs:53-60` 校验 data 目录含 `cmd_config.json`。

### 2.5 D06 单实例锁 — PASS（信号处理未自动验证）

实现：`src/lock.mjs:27-46` 用 `writeFile(..., {flag:'wx'})` 原子抢锁，`EEXIST` 时读锁并 `process.kill(pid,0)` 探活（`src/lock.mjs:8-11`，`EPERM` 视为存活），存活则抛 `ANOTHER_INSTANCE_RUNNING`（details: pid/port），不存活则删除 stale 锁重试；`release()` 只删自己 pid+startedAt 的锁（`src/lock.mjs:53-62`）；`update({port})` 先校验所有权再临时文件 + rename（`src/lock.mjs:63-70`）。

测试证据：同一 state 目录 `Promise.allSettled([acquireLock, acquireLock])` → 恰好 1 fulfilled、1 rejected 且 code 为 `ANOTHER_INSTANCE_RUNNING`、`details.pid === process.pid`；释放后可重新获取。人为写入 `{pid:999999,...}`（不可能存活的 pid）作为 stale 锁 → 获取成功，锁文件被重写为当前 pid 与端口 5000，释放后锁文件 ENOENT。锁的 `release` 不删他人锁已有既有测试覆盖（`test/lock.test.mjs`）。

**未自动验证**：Windows 下 `child.kill` 无法可靠触发 SIGINT/SIGTERM，因此 `src/server.mjs:104-105` 的“信号退出时释放锁”未在本次审计中自动验证（代码路径存在：`shutdown()` → `lock.release()` → `server.close()` → `process.exit(0)`）。按要求不为此卡住，列为未覆盖边界。

### 2.6 D03 令牌刷新存活 — PASS（单元级）

实现：`public/ui-state.mjs:17-51` 提供 `parseTokenHash/loadToken/saveToken/clearToken`，token 只进 `sessionStorage`，非法值不写、存储异常全部安全降级；`public/app.mjs:2,5,39` 从 hash 读取一次后 `history.replaceState` 清 hash，`refresh({persist:true})` 成功后写 `sessionStorage`。

测试证据：`parseTokenHash` 支持 `#token=`/`?token=`/裸 `token=`、百分号编码、空值/非字符串/畸形输入返回 `''` 不抛错；`saveToken` 拒绝 7 字符、含空格、非字符串；合法 64 字符 token 可存可读；`clearToken` 后读回 `''`；`storage` 为 `undefined` 或 `getItem/setItem/removeItem` 抛异常时分别返回 `''`/`false`/`false`。既有 `test/ui.test.mjs` 的 UI token 用例同时通过。
